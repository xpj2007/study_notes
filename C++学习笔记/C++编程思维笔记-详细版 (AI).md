## 第 0 章 先破一个误解

很多人说"C++ 就是 C 加上了类"。**这句话害人。**

如果只是"C 加类"，你会写出这种代码：

```cpp
// 这只是"带成员的 C 结构体"，不是 C++ 思维
struct Worker {
    int id;
    char name[32];
    int age;
};

void worker_set_age(struct Worker *w, int age) { w->age = age; }
void worker_print(struct Worker *w) { printf("%d %s %d\n", w->id, w->name, w->age); }
```

语法上它是 C++（能编译通过），但思维上**完全是 C**：

- 数据和操作分离
- 对象不能保证自己有效（`Worker w;` 里 `age` 是垃圾值）
- 资源释放靠人记

同样一个东西，C++ 思维是这样写的：

```cpp
class Worker {
    public:
        Worker(int id, std::string name, int age);   // 创建即有效
        void setAge(int age);                        // 校验内化在类里
        void print() const;                          // 行为属于对象
        const std::string &name() const;             // 返回引用，不拷贝

    private:
        int m_ID;
        std::string m_Name;
        int m_Age;
};
```

**区别不在有没有 `class` 关键字，而在于你在设计什么。**

第 0 章的结论：**学 C++ 不是学新语法，是换一套想问题的方式。**

## 第 1 章 C 思维与 C++ 思维的根本差异

### 1.1 一句话对照

| 维度    | C 思维             | C++ 思维           |
| ----- | ---------------- | ---------------- |
| 思考单位  | 步骤、函数            | 类型、对象            |
| 核心问题  | "怎么一步步算出结果"      | "数据归谁管，它何时生、何时死" |
| 数据与操作 | 分开的（struct + 函数） | 绑在一起（类）          |
| 有效性   | 靠约定和自觉           | 构造函数保证           |
| 资源管理  | 手动 free，靠记性      | 析构函数自动释放（RAII）   |
| 复用方式  | 函数指针、宏、复制粘贴      | 继承、虚函数、模板        |
| 错误处理  | 返回错误码            | 异常 / 返回值 / 类型区分  |
| 检查时机  | 运行期              | **尽量推到编译期**      |
| const | 常量               | **意图声明**（承诺不改）   |
| 多态    | 函数指针表 + 手动分发     | 虚函数，编译器帮你分发      |

### 1.2 三次思维转换

**转换一：从"步骤"到"生命周期"**

- C 问："这个函数做什么？"
- C++ 问："**这个对象从哪来？用到什么时候？谁销毁它？**"

**转换二：从"释放内存"到"管理资源"**

内存只是资源的一种。文件句柄、网络连接、锁、硬件寄存器、数据库连接，都是资源。

C++ 的答案是统一的：**把资源的生命周期绑在对象的生命周期上**（RAII）。

**转换三：从"运行期检查"到"编译期保证"**

- C 的写法：`if (p == NULL) return -1;` —— 运行期才知道
- C++ 的写法：用引用 `T&` 表示"一定有对象"，用 `const T&` 表示"一定有且不会改"
- **能在编译期挡住的错误，就不要留到运行期**

### 1.3 同一个需求，两种实现

需求：**读取一个文件，处理内容，关闭文件。**

```c
/* C 思维：容易漏掉 fclose —— 尤其当中间有多个 return */
int process(const char *path) {
    FILE *fp = fopen(path, "r");
    if (!fp) return -1;

    if (parse(fp) != 0) {
        return -2;          /* 忘了 fclose！文件句柄泄漏 */
    }
    if (check(fp) != 0) {
        return -3;          /* 又忘了 fclose！ */
    }

    fclose(fp);
    return 0;
}
```

```cpp
// C++ 思维：无论从哪个出口离开，文件都会自动关闭
void process(const std::string &path) {
    std::ifstream in(path);        // 构造时打开
    if (!in) throw std::runtime_error("open failed");

    parse(in);                     // 出错抛异常？
    check(in);                     // 中途 return？
    // 都不用管 —— in 析构时自动 close
}
```

**注意最后一行注释**：不管从哪条路离开这个函数 —— 正常返回、中途 `return`、还是抛异常 —— `in` 都会被析构，文件都会被关闭。

这就是 RAII 的威力：**它把"记得释放"变成了"不可能忘记"。**

### 模型一 所有权思维：C 想内存，C++ 想资源的生命周期

#### 核心问题

> **这块资源归谁？谁负责把它还回去？**

#### 三条规则

**规则 1：谁申请，谁释放 —— 而且要在同一个作用域里配对**

```cpp
// ❌ 申请在 A，释放在 B —— 迟早出问题
Object *make() { return new Object(); }

void use() {
    Object *p = make();
    // ... 中间可能 return / throw
    delete p;              // 只要有一条路径漏了，就泄漏
}

// ✅ 用一个对象包住它：栈对象自动析构
void use() {
    Object obj;            // 在栈上，离开作用域自动销毁
    // 什么都不用写
}
```

**规则 2：RAII —— 构造时获取，析构时释放**

```cpp
class FileHandle {
    public:
        explicit FileHandle(const std::string &path)
            : m_Fp(std::fopen(path.c_str(), "r")) {
            if (!m_Fp) throw std::runtime_error("open failed");
        }

        ~FileHandle() {
            if (m_Fp) std::fclose(m_Fp);      // 保证归还
        }

        // 禁止拷贝：两个对象关同一个文件会出问题
        FileHandle(const FileHandle &) = delete;
        FileHandle &operator=(const FileHandle &) = delete;

        std::FILE *get() const { return m_Fp; }

    private:
        std::FILE *m_Fp;
};
```

用的时候：

```cpp
void f() {
    FileHandle fh("data.txt");     // 打开
    // ... 随便怎么 return、怎么抛异常
}                                  // 这里自动关闭
```

**规则 3：区分"拥有"和"借用"**

| 关系 | 谁释放 | 参数怎么传 |
|---|---|---|
| **拥有** | 我自己 | 用值 / `unique_ptr`（独占） / `shared_ptr`（共享） |
| **借用（会改）** | 别人 | `T &` |
| **借用（不改）** | 别人 | `const T &` |
| **可能没有** | 别人 | `T *`（要判空） |

**这个表格值得背下来。** 写函数参数时对号入座，能避免绝大部分生命周期问题。

#### 自测

下面这段代码哪里有问题？

```cpp
Worker *find(int id) {
    Worker w(id, "temp");
    return &w;
}
```

> **答案**：`w` 是局部对象，函数返回时就被销毁了。返回的指针是**悬空指针**，使用它是未定义行为。
>
> C 里也有同样的问题（返回局部数组地址），但 C++ 里更容易犯，因为对象有构造函数和析构函数，销毁时还会执行代码（比如释放内部资源）。

### 模型二 值语义优先：C 习惯指针，C++ 默认用值

#### 核心问题

> **我需要的是"一份数据"还是"同一个对象的另一个名字"？**

#### 五种参数传递方式

```cpp
void f1(Widget w);                 // 拷贝一份（改它不影响外面）
void f2(Widget &w);                // 引用（会改到外面）
void f3(const Widget &w);          // 引用但只读（最常用）
void f4(Widget *w);                // 指针（可能为 nullptr）
void f5(Widget &&w);               // 右值引用（移动语义，进阶）
```

#### 实用选择顺序

| 场景 | 选择 | 理由 |
|---|---|---|
| 内置类型（int/bool/指针） | 传值 | 拷贝成本几乎为零，传值更简单安全 |
| 大对象、只读 | `const T &` | 不拷贝、不修改 |
| 大对象、要修改 | `T &` | 不拷贝、能改 |
| "可能没有对象" | `T *`（并判空） | 引用不能为空 |
| 需要副本 | 传值 | 语义清晰 |

**默认选 `const T &`** —— 这是最安全的"不拷贝"方式。

#### 为什么"值语义优先"

C 程序员的直觉是"传指针省拷贝"，于是到处用指针。但指针带来三个问题：

1. **可能为空** —— 每次用都要判空
2. **生命周期不明** —— 不知道这个指针指向的对象什么时候失效
3. **别名问题（aliasing）** —— 两个指针指向同一对象，改一个影响另一个

**值语义没有这些问题**：每个值都是独立的，改它绝对不会影响别人。

```cpp
// ❌ 到处是指针，读代码要时刻担心空指针和别名
void process(Widget *a, Widget *b) {
    if (!a || !b) return;
    a->value = b->value;        // 如果 a 和 b 是同一个对象呢？
}

// ✅ 值语义：a 是副本，绝对安全
void process(Widget a, const Widget &b) {
    a.value = b.value;          // a 是独立的副本，怎么改都不影响调用方
}
```

#### 什么时候才真的需要指针/引用

1. **多态**（要用基类指针调用虚函数）
2. **对象太大**，拷贝成本高
3. **必须共享同一份数据**（多个地方要看到同一个对象的修改）
4. **对象可能不存在**

除了这四种，优先用值。

### 模型三 面向接口：C 判断类型，C++ 发号施令

#### 核心问题

> **这个"判断类型"的动作，应该由谁来做？**

#### 反面模式：类型码 + if/else

```cpp
// ❌ 每个新类型都要修改这些函数
struct Shape {
    int type;            // 1=圆 2=方 3=三角
    double a, b;
};

double area(const Shape &s) {
    if (s.type == 1)      return 3.14159 * s.a * s.a;
    else if (s.type == 2) return s.a * s.b;
    else if (s.type == 3) return 0.5 * s.a * s.b;
    return 0;
}

void draw(const Shape &s) {
    if (s.type == 1)      drawCircle(s);
    else if (s.type == 2) drawRect(s);
    else if (s.type == 3) drawTriangle(s);
}
// 加"椭圆"？area 要改，draw 要改，print 要改……全部都要改
```

#### C++ 思维：让对象自己知道该怎么做

```cpp
class Shape {
    public:
        virtual ~Shape() = default;
        virtual double area() const = 0;
        virtual void draw() const = 0;
};

class Circle : public Shape {
    public:
        double area() const override { return 3.14159 * m_R * m_R; }
        void draw() const override { /* ... */ }
    private:
        double m_R;
};

// 使用：完全不需要知道具体类型
void renderAll(const std::vector<Shape *> &shapes) {
    for (const Shape *s : shapes) {
        s->draw();                          // 谁干的活，不用我管
        std::cout << s->area() << "\n";
    }
}
// 加"椭圆"？只写一个新类，上面这些代码一行都不用改
```

#### 判断信号

**只要你写出了 `if (type == ...)` 或者 `switch (type)`，就停下来问：**

> **这个判断能不能变成一个虚函数？**

能的话，说明这个判断是**对象的职责**，不该由调用方承担。

#### 继承 vs 组合

| | 关系 | 判断句 | 例子 |
|---|---|---|---|
| **继承** | is-a（是一种） | "B **是一种** A" | 圆是一种形状 ✅ |
| **组合** | has-a（有一个） | "A **拥有** B" | 车拥有引擎 ✅ |

```cpp
// ❌ 错用继承：引擎不是车的一种
class Car : public Engine { };

// ✅ 组合
class Car {
    Engine m_engine;
};
```

**经验法则：优先用组合，只在确实是 is-a 时才继承。** 继承耦合更紧（基类一改，所有子类受影响），组合更松。

#### 继承的两个铁律

**铁律一：基类析构函数必须是虚函数**

```cpp
class Base {
    public:
        virtual ~Base() = default;    // 必须写 virtual
};

Base *p = new Derived();
delete p;      // 没有 virtual → 只调用 ~Base()，Derived 的清理不执行 → 泄漏
```

**铁律二：不要在基类构造函数/析构函数里调用虚函数**

构造基类时派生类部分还没建好，虚函数不会派发到子类。结果是"你以为调了子类，实际调了基类"。

### 模型四 用类型表达意图：让非法状态无法出现

#### 核心问题

> **这个数据可能取哪些值？我能不能用一个类型把它限制住？**

#### 常见做法

```cpp
// ❌ 用 int 表示状态：可以是任何值，包括非法的 99
int state = 99;      // 什么意思？

// ✅ 用 enum class：只能是这几个值之一
enum class State { Idle, Running, Stopped };
State s = State::Idle;
```

```cpp
// ❌ 用 int 表示端口号：可以是 -1、100000
int port = -1;

// ✅ 用一个类型封装范围校验
class Port {
    public:
        explicit Port(int v) {
            if (v < 1 || v > 65535) throw std::out_of_range("bad port");
            m_Value = v;
        }
        int value() const { return m_Value; }
    private:
        int m_Value;
};
// 现在 "一个 Port 对象存在" 就意味着 "端口号合法"
```

#### 思维习惯

写每个成员变量时问三句：

1. **它的取值有约束吗？**（年龄 1~150、端口 1~65535）
2. **约束由谁保证？** 靠调用方自觉，还是类自己？
3. **能不能用类型表达这个约束？**

**把约束内化到类型里**，比在十处地方写 `if` 检查可靠得多。

#### 意图 → 类型对照表

| 意图 | 表达方式 |
|---|---|
| "一定存在" | 引用 `T &` |
| "可能不存在" | 指针 `T *` / `std::optional` |
| "独占所有权" | `std::unique_ptr<T>` |
| "共享所有权" | `std::shared_ptr<T>` |
| "只是借用" | `T &` / `const T &` |
| "只能是这几个值" | `enum class` |
| "范围受限的数值" | 封装成一个类 |

### 模型五 const 是设计语言

#### 核心问题

> **这个操作会改变对象的状态吗？**

- 不会 → 加 `const`
- 会 → 不加

#### 三处用法

```cpp
class Buffer {
    public:
        // 1. const 成员函数：承诺不修改本对象
        std::size_t size() const;

        // 2. const 引用返回：不拷贝 + 调用方不能改
        const std::string &name() const;

        // 3. const 参数：承诺不修改传进来的对象
        void compare(const Buffer &other) const;
};
```

#### 为什么 const 是"思维"而不是"语法"

**const 强迫你区分"查询"和"修改"。** 这个区分是良好设计的基础。

```cpp
// 加 const 时，编译器会检查你的承诺是否兑现：
void save() const {
    writeToFile(...);          // OK，不改对象
    m_Count++;                 // ❌ 编译错误：你在 const 函数里改成员
    m_Data.push_back(x);       // ❌ 同上
}
```

**编译器的报错在帮你做设计评审。** 一个"保存"操作凭什么修改对象状态？如果编译不过，往往说明**你的设计有问题**，而不是 const 写错了。

#### 实用规则

1. **所有不修改对象的成员函数都加 `const`**
2. **返回大对象时用 `const T &` 而不是 `T`**（避免拷贝）
3. **函数参数默认用 `const T &`**
4. 遇到"const 编译不过"，**先怀疑设计，再怀疑语法**

### 模型六 编译期思维：能编译期定就不要运行期算

#### 核心问题

> **这件事能不能在编译时就确定？**

#### 常见手段

```cpp
// ❌ 宏没有类型，不受作用域约束
#define MAX_SIZE 100

// ✅ 编译期常量
constexpr int kMaxSize = 100;

// ✅ 编译期计算
constexpr int square(int x) { return x * x; }
int arr[square(4)];           // 编译期就确定了大小

// ✅ 编译期断言：条件不满足直接编译失败
static_assert(sizeof(int) == 4, "int 必须是 4 字节");
```

#### 为什么重要

**编译期发现的错误，修复成本是运行期发现的百分之一。**

```cpp
// 运行期：可能上线才炸
int *p = get();
if (p == nullptr) return;      // 忘了这句，运行时崩溃

// 编译期：写错就编译不过
void f(int &value);            // 引用不能为空，一定指向有效对象
```

#### 检查时机对照

| 手段 | 检查时机 | 性能 |
|---|---|---|
| `#define` | 预处理，无类型检查 | 无开销但危险 |
| `constexpr` | **编译期**，有类型检查 | 无开销 |
| `static_assert` | **编译期** | 无开销 |
| `assert` | 运行期（Debug） | Debug 有开销 |
| `if` 检查 | 运行期 | 有开销 |

**优先用上面的，不要用 `#define` 定义常量。**

## 第 3 章 训练方法

看完六大模型，你可能"懂了"但还不会用。**思维只能靠练出来。**

### 方法 1：刻意重写（最有效）

**核心**：合上教程，凭记忆从零写。

操作步骤：

1. 找一个你跟着教程做过的小项目
2. **新建一个空文件夹，不看任何参考**
3. 从头写，卡住了不要立刻查
4. 卡住时先问自己："这里需要什么数据？谁拥有它？我想要什么行为？"
5. 写完再和旧代码对比 —— **差异就是你的知识漏洞**

**为什么有效**：跟着教程敲时，"下一步写什么"是视频告诉你的。重写时，这个决策必须由你自己做 —— **这才是真正的能力**。

**频率**：每个阶段学完重写一次。第一次可能要一整天，第三次就快了。

### 方法 2：故意搞坏（理解原理最快的路）

把正确的代码改坏，**亲眼看到后果**，比读十篇文章都管用。

| 动手改 | 预期现象 | 你学到的 |
|---|---|---|
| 去掉基类的 `virtual ~Base()` | 派生类析构不执行 / 内存泄漏 | 虚析构的必要性 |
| 去掉 `showInfo()` 的 `virtual` | 调用的永远是基类版本 | 虚函数派发机制 |
| 去掉所有 `delete` | 内存持续增长（任务管理器可见） | 泄漏是怎么发生的 |
| 把 `const` 删掉 / 加上 | 编译错误的出现和消失 | const 的传染性 |
| 注释掉 `if (n == 0) return;` | 空容器时崩溃 | 边界条件的重要性 |
| 把 `int` 改成 `char` 再 `cout` | 输出变成乱码字符 | 类型宽度的影响 |
| 把引用参数改成传值 | 修改没生效（改的是副本） | 值语义 vs 引用语义 |
| 故意返回局部变量的地址 | 悬空指针，结果随机 | 生命周期 |

**关键**：改坏 → 观察 → 修好。**自己修好的，才是真的懂了。**

### 方法 3：用调试器而不是打印

```cpp
// ❌ 初学者常用：靠打印猜
std::cout << "here1" << std::endl;
std::cout << "num=" << num << std::endl;
```

**必须掌握的操作**：

| 操作 | 用途 |
|---|---|
| 设断点 | 程序跑到这里停住 |
| 单步跳过（Step Over） | 执行下一行，不进函数 |
| 单步进入（Step Into） | 进到函数里面看 |
| 查看变量 | 看当前所有变量的值 |
| 查看调用栈 | 我是被谁调用的？ |
| 条件断点 | `i == 5` 时才停 |
| 监视表达式 | 盯着 `*ptr` 的值变化 |

**特别推荐**：单步进入一个虚函数调用，看它怎么"自动"选到正确的实现。**亲眼看过一次，多态就不是抽象概念了。**

### 方法 4：给代码写"设计说明"

写代码**之前**，先写三到五行：

```
类：FileHandle
职责：管理一个文件的生命周期
拥有：FILE*（独占，负责关闭）
不负责：文件内容的解析（那是调用方的事）
初始化：构造函数打开文件，失败抛异常
清理：析构函数关闭文件
```

**说不清的类，就是没设计好的类。**

### 方法 5：用四个问题读代码

读别人的代码，也读自己的代码。每读一个类/函数，问：

1. **它拥有什么资源？谁负责释放？**
2. **它的前置条件是什么？由谁保证？**（参数能是空吗？能是负数吗？）
3. **如果加一个新类型/新需求，要改几处？**
4. **函数名说的事情，和它实际做的事一致吗？**

这四个问题能揪出绝大多数设计问题。

### 方法 6：刻意寻找"重复"和"类型判断"

| 信号 | 说明 | 应该怎么做 |
|---|---|---|
| 多处出现相同代码 | 重复 | 提到基类 / 抽成函数 |
| `if (type == 1) ... else if (type == 2)` | 类型判断散落 | 考虑虚函数 |
| 一个类里全是 get/set | 没有行为 | 重新思考职责 |
| 函数名与实际行为不符 | 名不副实 | 改名 或 拆函数 |
| 成员变量之间有隐含约束 | 可能进入非法组合 | 用类型/枚举封装 |

概念：RAII

## 第 4 章 自查清单

写完一个类，对照检查。**建议打印出来贴在显示器旁。**

### 4.1 类的基本检查

- [ ] 类名是**名词**吗？（`Worker` ✅ / `DoProcess` ❌）
- [ ] 我能用**一句话**说清这个类的职责吗？
- [ ] 这个类**拥有**什么资源？析构函数释放了吗？
- [ ] 对象**创建出来就有效**吗？（构造函数做了校验吗？）
- [ ] 有没有"半初始化"的状态？（某些成员没赋值）
- [ ] 成员变量是 `private` 吗？

### 4.2 接口检查

- [ ] 接口是不是太宽了？（有没有一堆无脑 get/set）
- [ ] 每个 `get`/`set` 都真的需要吗？
- [ ] 函数名和它做的事**一致**吗？（`getXxx` 有没有偷偷打印或修改？）
- [ ] 不修改对象的函数都加 `const` 了吗？
- [ ] 返回大对象时用引用了吗？（`const T &` 而不是 `T`）
- [ ] 参数用 `const T &` 了吗？

### 4.3 继承检查

- [ ] 真的是 is-a 关系吗？
- [ ] 基类析构函数是 `virtual` 吗？
- [ ] 有没有在构造/析构函数里调用虚函数？
- [ ] 派生类用了 `override` 吗？（能帮你发现签名写错）
- [ ] 有没有"为了复用代码"而继承？（那应该用组合）

### 4.4 资源与拷贝检查

- [ ] 谁 `new`，谁 `delete`？配对吗？
- [ ] 有多个 `return` 路径时，资源都能释放吗？
- [ ] 抛异常时资源能释放吗？（RAII 才能保证）
- [ ] 如果类持有资源，拷贝构造/拷贝赋值/析构函数三者都考虑了吗？
- [ ] 如果写不出正确的拷贝，是不是该 `= delete`？

### 4.5 行为检查

- [ ] 有没有隐藏的副作用？
- [ ] 同样的输入，永远得到同样的输出吗？（可测试性）
- [ ] 边界情况考虑了吗？（空、0、负数、最大长度）

## 第 5 章 常见坏味道

看到这些信号，说明设计需要改。

| 坏味道 | 症状 | 怎么改 |
|---|---|---|
| **数据袋子** | 类里全是 get/set，没有真正的方法 | 想清楚职责，把行为搬进来 |
| **名不副实** | `getName()` 却会打印或改状态 | 改名，或拆成两个函数 |
| **类型码 + 分支** | 到处 `if (type == 1)` | 用多态（虚函数） |
| **重复代码** | 多个类有几乎一样的实现 | 提到基类或抽成函数 |
| **脆弱的基类** | 改基类导致一堆子类出问题 | 减少继承，优先组合 |
| **构造函数太重** | 构造里读输入、连网络、开窗口 | 构造函数只做初始化 |
| **魔法数字** | 代码里散落 `100`、`3.14` | 用具名常量 |
| **过长函数** | 一个函数几十上百行 | 按职责拆小 |
| **全局变量** | 到处 `extern` 全局状态 | 封装进类，通过参数传递 |
| **头文件污染** | 头文件里 `using namespace std;` | 头文件用完整限定名 `std::string` |
| **宏定义常量** | `#define MAX 100` | 用 `constexpr` |
| **所有权不明** | 不知道谁该 delete 某个指针 | 用 `unique_ptr` 明确表达 |

## 第 6 章 嵌入式背景的特别说明

有 C 和嵌入式基础的人学 C++，有独特优势和独特陷阱。

### 6.1 你的优势

| 你已经会的 | 在 C++ 里的价值 |
|---|---|
| 指针、内存布局 | 理解引用、智能指针、对象模型非常快 |
| 栈 / 堆的区别 | 一学 RAII 就懂为什么栈对象自动析构 |
| 手动内存管理 | 会**真正珍惜** RAII，而不是当成语法糖 |
| 位运算、字节序 | 学序列化、二进制协议更容易 |
| 资源受限经验 | 天然的"零开销"意识 |

### 6.2 C++ 在嵌入式的四个常见顾虑

**顾虑 1："虚函数太慢"**

- 虚函数开销 = 一次间接跳转 + 一次内存读
- **和 C 里用函数指针表做多态完全一样**
- 如果你在 C 里用过函数指针表（驱动抽象层、状态机），你早就在用同样的机制
- 真正慢的是糟糕的算法和多余的拷贝，不是虚函数

**顾虑 2："C++ 会偷偷分配内存"**

- 只有在**你写了** `new`、容器、`std::string` 时才会分配
- 用 C++ 编写但**不使用动态分配**的代码完全可行（很多嵌入式项目这么做）
- 关键能力是**知道哪些特性会分配**（`std::vector`、`std::string`、`std::function` 会）

**顾虑 3："异常开销大"**

- 很多嵌入式工具链支持 `-fno-exceptions`，此时异常机制完全不生成代码（零开销）
- 不用异常也能用 RAII —— 只要没有 `throw`，析构依然会在 `return` 和正常退出时执行

**顾虑 4："代码体积变大"**

- 不用的特性不会进二进制（这是 C++ 的核心设计原则）
- 但模板会为每个实例化生成代码，需要注意

### 6.3 RAII 在嵌入式的真实价值

这是 C++ 对嵌入式最大的贡献。

```c
/* C 思维：容易忘记恢复中断 */
void critical_section(void) {
    uint32_t primask = disable_irq();
    if (error) {
        enable_irq(primask);        /* 每个出口都要记得恢复 */
        return;
    }
    /* ... */
    enable_irq(primask);
}
```

```cpp
// C++ 思维：无论怎么退出，中断都会恢复
class IrqGuard {
    public:
        IrqGuard()  { m_Primask = disable_irq(); }
        ~IrqGuard() { enable_irq(m_Primask); }

        IrqGuard(const IrqGuard &) = delete;
        IrqGuard &operator=(const IrqGuard &) = delete;

    private:
        uint32_t m_Primask;
};

void critical_section() {
    IrqGuard guard;          // 关中断
    if (error) return;       // 自动恢复，不会忘记
    // ...
}                            // 自动恢复
```

**同样的模式适用于**：SPI/I2C 总线占用、看门狗喂狗、电源域开关、互斥锁、日志缓冲。

### 6.4 需要转变的 C 习惯

| C 习惯 | 为什么在 C++ 里要改 |
|---|---|
| 到处用裸指针 | 生命周期不明；用值 / 引用 / 智能指针表达意图 |
| `malloc/free` | 用 `new/delete`；但更好的是**根本不动态分配** |
| `goto cleanup` 统一释放 | RAII 天然解决，不需要 goto |
| 用宏定义常量和"函数" | 用 `constexpr` / `inline` 函数（有类型检查） |
| 用错误码层层返回 | 可以用异常（如果工具链支持），或保持错误码同时用 RAII |
| `struct` + 全局函数 | 类：数据 + 行为 + 保证有效 |

## 第 7 章 常见误区

### 误区 1："用了 class 就是 C++ 思维"

```cpp
// 这只是"带成员的 struct"
class Point {
    public:
        int x, y;              // public 数据，没有行为
};
void move(Point *p, int dx, int dy) { p->x += dx; p->y += dy; }
```

C++ 思维是**把行为放进去、把数据藏起来**：

```cpp
class Point {
    public:
        void move(int dx, int dy) { m_X += dx; m_Y += dy; }
        int x() const { return m_X; }
        int y() const { return m_Y; }
    private:
        int m_X = 0, m_Y = 0;
};
```

### 误区 2："继承是为了复用代码"

**继承的真正含义是"是一种"，不是"能省几行代码"。**

想复用代码，用**组合**或**提取公共函数**。为了复用而继承，会造出"栈继承自数组""经理继承自职工"这种不合理的关系。

### 误区 3："引用就是不能为空的指针"

语法上像，但**思维上完全不同**：

| | 指针 | 引用 |
|---|---|---|
| 语义 | "可能指向某个对象" | "就是这个对象" |
| 可否为空 | 可以 | 不可以 |
| 可否改指向 | 可以 | 不可以 |
| 用在哪里 | 需要"可选"时 | 默认选择 |

**用引用的意思是："我保证这里有对象。"** 这是把检查从运行期推到设计层。

### 误区 4："构造函数里做的事越多越好"

```cpp
// ❌ 构造函数里读用户输入、弹对话框、连网络
Database() {
    std::cout << "请输入密码：";
    std::cin >> m_Password;
    connect();
}
```

问题：这个类**没法测试**、**没法复用**、**创建失败不好处理**。

```cpp
// ✅ 构造函数只做初始化
Database(const std::string &password) : m_Password(password) {
    connect();      // 失败抛异常，语义清晰
}
// 用户输入是调用方的事
```

**原则：构造函数只负责"把对象建好"，不负责"和用户交互"。**

### 误区 5："早点优化性能"

- 虚函数、返回值拷贝、`std::string` 的开销，**在绝大多数场景下无关紧要**
- 真正的性能问题来自：糟糕的算法、不必要的深拷贝、频繁的堆分配
- **先写清楚，再测性能，最后才优化**（而且要有测量数据）

### 误区 6："C++ 太难，学不完"

- **没有人学完 C++**，工作十年的工程师也在查文档
- 目标不是"学完"，而是"**能用它做好一件事**"
- 先掌握 20% 的常用特性（类、继承、多态、RAII、STL 基础），足够应付大部分工作
- 剩下的边用边学

### 误区 7："能编译通过就是对的"

编译通过只说明语法对。设计对不对，要看：

- 资源会不会泄漏
- 边界情况会不会崩
- 加新功能要改多少地方
- 别人能不能看懂

**编译器的警告要清零** —— 它在帮你做设计评审。

## 附录：一页速查

### 参数怎么传

| 需求 | 写法 |
|---|---|
| 小的内置类型 | `T v` |
| 大对象只读 | `const T &v` |
| 大对象要改 | `T &v` |
| 可能没有 | `T *v`（判空） |

### 什么时候加 virtual

| 场景 | 加吗 |
|---|---|
| 基类析构函数 | **必须加** |
| 需要子类重新实现的行为 | 加 |
| 只是想在子类里复用实现 | **不加**（用组合或普通函数） |

### 写类的四问

1. 它代表什么现实事物？
2. 它必须维护哪些数据？
3. 它必须会做什么（自己的职责）？
4. 它和别的类是什么关系（is-a / has-a）？

### 核心口诀

> **资源绑生命周期，数据行为在一起，接口要窄要准，能编译期挡就编译期挡，能用在栈上就别放堆上，能不加虚函数就不加。**
